# Code review: WiFi Terminal, 2026-10-11

Reviewed: baseline 0.1.0 (John's `wifiterm.tar`, unchanged). Firmware `main/*.c`,
client `client/*.py` and its `tasks/`, `term/`, `cmdlib/` packages.
Nothing was built or run on hardware; findings are from reading the code. Where a
finding depends on SDK behaviour I could not check, it says so.

## 1. Summary

The fragility on mode changes has three root causes, in order of impact:

1. **Two threads read the keyboard at once.** In the client, command mode reads with
   `input()` on the main thread while the terminal reader thread may still be blocked
   in `select()`/`read()` on the same stdin, and the main thread flips the tty between
   raw and cooked underneath it. Whichever thread wins gets the keystroke.
2. **Mode is signalled in-band, and the firmware has no command mode.** The client sends
   `<CMD MODE>\r\n`, `<RAW MODE>\r\n`, `ping`, `reboot`, etc. on the same stream that the
   firmware copies straight to the RS-232 port. The device receives them as if typed, and
   its output cannot be told apart from command replies.
3. **Firmware buffer sizes don't agree, and one mismatch stalls the SSL to UART path
   permanently.** Any single TLS read of 64 bytes or more (a paste, or one of the
   hex-encoded `Tx..` commands from `cfgcmds.py`, which are 4 bytes per character) can
   never be read out of the message buffer, so it blocks everything behind it until reboot.

Mode switches are exactly when (1) and (2) collide: a burst of text in both directions,
a tty mode change, and a thread handover, all at once.

Also important: **the uploaded client does not run as-is** (section 4). It looks like a
snapshot taken mid-refactor, so I need to know which version is the one that worked.

## 2. Mode switching, end to end

What happens when you press ESC in serial mode (`client/wifiterm.py`):

1. Terminal reader thread (`ITask` via `IOTask`) reads one byte in raw mode and queues it.
2. Main loop sees `retstr[0] == ESC` (`wifiterm.py:168`), sets `cmdmode = True`.
3. Next pass: `term.set_readline()` restores cooked tty (`unixterm.py:131`), then
   `term.pause()`. Pause only clears an Event; the reader thread notices it at the
   *bottom* of its loop (`taskloop.py:32`). If it is inside `select()` with a 1 s timeout,
   it is still reading stdin, now in cooked mode, so it calls `readline()` and swallows
   the first command line you type.
4. `send_cmdmode()` puts `<CMD MODE>\r\n` on the SSL send queue. The firmware forwards it
   verbatim to the RS-232 device (`appmain.c:80-86`).
5. `cli.nextcmd()` blocks in `input()` (`cmdlib.py:542`). While blocked, nothing drains
   `sslconn.recvtask`, so device output accumulates and is printed in one lump after the
   next command, mixed with any command reply.

Going back to serial mode (`exit`), `set_rawmode()` is called before `term.run()`, while
the old reader thread may still be in `readline()`.

Other mode-switch hazards:

- **ESC is a poor escape key.** Arrow keys, Home/End, F-keys and Alt-combinations all
  send sequences beginning with ESC, so they trigger command mode and the rest of the
  sequence (`[A` etc.) leaks into the command line or the device. Only `retstr[0]` is
  checked, so an ESC in the middle of a chunk is sent to the device instead.
- Command replies and device output arrive on the same queue with no marker.
- `send_cmdmode` logs "switch to command mode" in both branches (`wifiterm.py:25,28`), which
  makes the debug log misleading when chasing this exact problem.

## 3. Firmware findings (`main/`)

Severity: **H** breaks or stalls, **M** intermittent or data loss, **L** hygiene.

| # | Sev | Where | Finding |
|---|---|---|---|
| F-01 | H | `appmain.c:40,80` | SSL read buffer is 255 bytes, but `app_main` reads it into a 64-byte buffer. FreeRTOS `xMessageBufferReceive` leaves a too-long message at the head of the buffer and returns 0, so every later message is stuck behind it. The SSL to UART path is dead until reboot. |
| F-02 | H | `ssl.c:121,212` | `ssl_read_task` and `ssl_write_task` call `mbedtls_ssl_read` and `mbedtls_ssl_write` on the same `mbedtls_ssl_context` concurrently. mbedTLS does not support that, even with `MBEDTLS_THREADING`. Corrupts record state under simultaneous traffic in both directions, which is what a mode switch produces. |
| F-03 | H | `ssl.c:352,365`, `sslfuncs.c:196-197` | On reset, read/write tasks are `vTaskSuspend`ed wherever they are, possibly inside mbedTLS or lwIP holding a mutex, then `mbedtls_ssl_session_reset` runs on the context they were using. Can deadlock or corrupt on reconnect. |
| F-04 | M | `msgbuf.c:62,104`; `ssl.c:213`; `uart.c:139` | `MSGBUF_DATA.msglen` and `.status` are written by both producer and consumer. The consumer then uses `msglen` as the length to send, so a concurrent write by the producer changes how many bytes go out. |
| F-05 | M | `ssl.c:117,273` | 255-byte reads go into a 256-byte message buffer. Each message needs 4 extra bytes for its length, so reads over about 252 bytes can never be stored and are dropped. |
| F-06 | M | `appmain.c:48,90`; `msgbuf.c:133` | A 128-byte UART chunk can't be NUL-terminated in the 128-byte buffer, so it is consumed and silently dropped. |
| F-07 | M | `msgbuf_write_str`, `msgbuf_read_str` | Data is treated as C strings, so `strlen` truncates at any 0x00 byte. Not binary-safe (Ctrl-@, binary protocols, some terminal control sequences). |

General: the `Task`/`QTask`/`ITask`/`OTask`/`IOTask`/`DataLib` stack is a lot of machinery
for two byte streams. Pause/resume via Events can't interrupt a blocking read, which is the
mechanism behind section 2 step 3. DEBUG logging of every queue poll (every 10 ms) makes
the logs huge (`debug.log` is 4,271 lines for a short test).

## 5. Recommended approach

### Firmware
- **One task owns the TLS session.** A single bridge task loops on `select()` over the
  client socket with a short timeout, and on a FreeRTOS notification from the UART side.
  It does all `mbedtls_ssl_read`/`write` calls itself. No suspend/resume; on error it
  closes, frees, and goes back to `accept`. Fixes F-02, F-03, F-10.
- **Byte streams, not messages or strings.** Use `xStreamBuffer` (UART RX to TLS, TLS to
  UART TX) with `uint8_t` buffers and explicit lengths. Fixes F-01, F-04 to F-07.
- **Move the device off the console UART.** Call `uart_enable_swap()` so UART0 data uses
  GPIO13/GPIO15 (RX/TX), and send logs to UART1 TX on GPIO2. The device then never sees
  boot or log output. Needs a wiring change, so it's your call. Fixes F-08.
- **No reboot on disconnect.** Keep the AP up and return to `accept`. Fixes F-09.
- **Commands handled in the firmware** via the framed protocol below, with UART settings
  and WiFi credentials stored through `nvslib.c`.

### Protocol (ADR-0003, proposed)
Length-prefixed frames on the one TLS connection: `type | len | payload`, with types
DATA, CMD, RESP, EVENT. The ESP8266 has no modes. "Command mode" becomes a client display
state only, so switching modes sends nothing to the device and can't race anything.

### Client
- **One thread reads stdin, always.** Keep the terminal in raw mode for the whole session
  and do line editing for command mode in the main loop (a small line editor, or
  `prompt_toolkit` if you're happy adding a dependency). Nothing ever needs pausing.
- **asyncio instead of threads.** `asyncio.open_connection(ssl=ctx)` plus a stdin reader
  gives one event loop, no locks, no Events, and clean shutdown. This would replace the
  `tasks/` package (about 700 lines) with roughly 150.
- **A dedicated escape key**, such as Ctrl-] (telnet's) or Ctrl-T then a letter (pyserial
  miniterm's), so arrow keys and the device's own escape sequences pass through untouched.
- **Bytes end to end**, decoding with `errors="replace"` only for display.
- **Logging at INFO by default**, with DEBUG on a flag.

### Suggested order
1. Get a known-good baseline: either the working version you have, or fix C-01 to C-13
   minimally so this snapshot runs (0.1.x).
2. Firmware F-01 and F-02/F-03 (single TLS owner, stream buffers): fixes the stalls with no
   protocol change (0.2.0).
3. Framed protocol plus client rewrite together (0.3.0).
4. UART pin swap and NVS-backed settings (0.4.0).

Each step would be a separate commit with a CHANGELOG entry, and nothing gets built or
flashed until you say so.
